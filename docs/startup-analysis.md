# 시작 로딩 분석 — v0.2.27

## 시작 조회 생략 및 세부 초기화 추적 — v0.2.30

사용자 요청에 따라 시작 시 상품 목록 조회를 생략한다. MPAuthFlowState.OnAuthenticationStatus의 GetMarketCatalog 호출 1곳만 변경했다. SteamMarketService.Catalog에 원래 실패 시 쓰는 빈 SteamMarketCatalog를 설정하고 이미 구독된 OnMarketCatalogRetrieved에 통지한다. 이후 원래 MPAuthFlowState.OnMarketCatalogRetrieved가 인벤토리 조회를 시작한다. 인벤토리 Load가 Catalog.GetItem을 통해 아이템을 해석하는 의존성을 확인했다. 따라서 로컬 ProfileItemAttributes의 MarketItemID/ID를 별도의 대응표로 유지하고 빈 목록 카탈로그의 ID/속성 ID/통화 조회에만 대체 값을 제공한다. Items/VirtualCurrencies 표시 목록은 비워 두며 실제 SDK 인벤토리 응답 및 기존 AlwaysOwned 처리만 소유권을 결정한다. 없는 ID는 null로 유지한다. Steam 인증·프로필·인벤토리 경로와 독립적인 상점 조회 메서드는 유지한다. 실제 서비스 객체를 null Runner로 생성한 복사본 테스트에서 빈 목록/공개 Catalog/완료 이벤트 1회 전달을 확인했으며, Steam 연결을 요청하지 않았다. 이전 상품 대기 90초 또는 v0.2.29의 최대 15초를 시작 경로에서 제거하는 변경이다. 새 버전의 전체 메뉴 도달 시간은 미측정이다.

장면 코드를 조사해 MainComponent의 자식 장면 순차 로딩과 SceneLoader의 재귀 코루틴을 확인했다. 순서를 강제로 바꾸거나 병렬화하면 Awake/Start 및 UI 계층 조립의 의존성이 달라질 수 있어 유지했다. 대신 시작 중 동일 SceneLoader·동일 목록의 완료된 반복 실행만 생략한다. 실패/취소/목록 변경은 재실행한다. 메뉴 이후는 원래 로딩을 그대로 반환한다. 실제 중복이 발생하지 않으면 이 부분의 시간 절약은 없다. 테스트 코루틴으로 yield·완료·재시도·메뉴 이후 경로를 검증했다.

ServiceContext.GetDependencies는 이미 타입별 캐시를 사용하고 있었다. 캐시를 추가해 4.5~9초를 줄일 수 있다는 근거는 없었다. 어떤 서비스의 SetUp/PostSetUp이 오래 걸리는지와 OrcaUI.SetupFE/BootflowServicesBindState.BindServices 범위를 기록하도록 했다. 이는 남은 병목을 측정하는 변경이며 서비스 초기화 시간이 단축됐다는 의미는 아니다. 초기화 호출 목록과 순서는 복사본의 원본 IL과 비교했다.

## 후속 진단 및 수정 — v0.2.29

2026-10-22 01:49:03 실행에서 메뉴 상태 진입까지 119.989초가 기록됐다. 이 중 상품 목록 요청은 01:49:32.204~01:51:02.211, 90.007초였다. 인증은 0.058초, 인벤토리는 0.887초, 프로필은 0.017초, 통계는 0.043초, 경기 기록은 0.031초였다. 상품 목록이 전체의 약 75%를 차지했다. 앞선 01:40 실행의 상품 목록은 0.608초였으므로 초기 장면/서비스 초기화와 구분되는 간헐적 대기다.

설치 DLL에서 SteamTask<T>가 기본 제한 시간을 90초로 설정하고 SteamRunner.InternalUpdate가 해당 시간을 넘기면 기존 시간 초과 상태로 전환하는 코드를 확인했다. 상품 목록 실패 시 SteamMarketService.HandleMarketCatalogRetrieved는 빈 SteamMarketCatalog를 만들어 콜백을 통지하고, 이후 인벤토리 및 프로필 조회가 진행된다. 따라서 상품 목록 요청 객체 생성자에서 protected mTaskTimeout만 15초로 지정했다. 전역 제한 시간을 바꾸지 않았다. 기본 콜백 해제·요청 종료·상점 대체 경로는 보존했다. 응답이 15초보다 느린 경우 상점 목록/가격 가용성과 대기 시간을 교환하는 변경이다.

복사본의 실제 SteamGetMarketCatalogTask 생성자를 실행해 TaskTimeout=15, 일반 SteamTask<object> 생성자를 실행해 90을 검증했다. 나머지 Steam 메서드들의 IL이 동일한지 비교했고, 7개 DLL과 설정/데이터의 정확한 복원을 검증했다. 네트워크 요청 Execute 및 실제 게임은 테스트 중 실행하지 않았다. 수정 후 전체 로딩 시간과 정상 상점 표시의 실제 경기 확인은 남아 있다. 동일 실패 조건이라면 상품 대기는 약 75초 짧아질 것으로 예상되지만 전체 로딩 시간 보장값은 아니다.

2026-10-22, 설치 파일을 변경하지 않고 기존 output 로그와 Player.log, 설치 DLL의 원본 백업을 분석했다.

## 코드에서 확인한 순서와 변경

MainComponent.Awake → 자식 장면 로딩 → Main.Startup → GlobalServiceInitState → ApplicationAssetBundleLoadingState → BootflowServicesInit/Bind → MPAuthFlowState → MainMenuFlowState 흐름을 조사했다. 인증 후에는 시장 목록, 인벤토리, 프로필, 통계, 경기 기록 등의 요청·콜백이 이어진다. 원래 완료 조건과 순서를 유지했다.

기존 High backgroundLoadingPriority 후크는 사전 로딩 상태에 진입한 뒤에만 켜졌다. 따라서 그 이전 장면 로딩에는 적용되지 않는 범위 문제가 있었다. Awake 시작에 같은 설정을 적용하고 사전 로딩 종료에 복원한다. 메뉴 진입 시에도 복원을 시도한다. 이는 초기 비동기 로딩에 적용되는 설정 범위 보완이며 앞서 관찰한 정지의 원인이 이 설정이었다고 입증한 것은 아니다.

새 진단은 단조 증가하는 Stopwatch로 동기 호출과 비동기 요청 대기를 구분한다. 시작 지점에는 프로세스 생성 후 경과 시간도 기록한다. 네트워크 요청 콜백의 성공 여부와 인증 상태를 기록하며 토큰·사용자 프로필 내용은 기록하지 않는다. 매 프레임 디스크 기록은 추가하지 않았다. 메뉴 흐름 진입 후 진단을 종료하고 중단된 범위가 있으면 unfinished scope로 남긴다. 일부 비동기 요청이 즉시 시작에 실패하고 콜백을 주지 않으면 종료 시간이 확정되지 않으므로 이를 임의로 0초로 계산하지 않는다.

## 검증과 실제 실행 비교 절차

- 게임 복사본에 적용하고 전체 대상 파일이 원래 바이트로 복원되는지 확인한다.
- 변경한 실제 초기화 메서드들의 기존 호출 목록과 예외 처리 개수가 유지되는지 확인한다.
- 분기·반환값·catch/finally를 가진 코드에 같은 삽입 처리를 적용해 실행 결과를 비교한다.
- 유닛·HUD·치트·에너지·Steam 실행 경로와 업데이트 설치/복구 테스트를 실행한다.

현재 설치 파일을 자동 변경하지 않는 요청에 따라 새 패치로 실제 게임을 실행하지 않았다. 수정 후 측정값은 아직 없다. 적용 후 비교할 때는 동일 Steam 로그인 상태·게임 설정으로 재부팅 후 첫 실행과 즉시 재실행을 각각 따로 기록한다. 첫 로딩 화면부터 실제 메뉴가 조작 가능한 순간까지를 외부 시계 또는 영상으로 측정하고, 해당 output 로그의 Startup 단계 시간과 함께 비교한다. 진단의 main-menu flow ready는 화면 렌더링 완료와 구분한다. 동일 조건에서 최소 3회씩 확보한 뒤 중앙값을 비교한다. 인증 실패나 창 비활성 상태가 섞인 실행은 별도로 분류한다.
